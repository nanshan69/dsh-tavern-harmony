# 移植说明：从桌面 DSH 到鸿蒙 DSHM

上游 `dsh-tavern` 假设自己跑在桌面 DSH 上：有 node 可执行文件、能 fork、
V8 带 JIT/WASM、插件安装走 pnpm、宿主目录可写。DSHM 把这些前提全部改掉了。
这篇记下每条约束、对应的改写，以及为什么没用别的方案。

## 约束清单

| # | 端侧事实 | 上游怎么做 | 后果 |
| --- | --- | --- | --- |
| 1 | `process.execPath` 是 `/system/bin/appspawn`，spawn 它 `EACCES` | `child_process.fork` 跑模板引擎 | 模板引擎完全不可用 |
| 2 | Node 24 **jitless**：没有 `WebAssembly`，eval 慢 | 依赖 WASM（部分第三方）/ JIT 热路径 | worker 里初始化即崩；模板渲染慢 |
| 3 | `createRequire(parent).resolve.paths` 在端侧构建里缺失 | 依赖它做 CJS 解析 | jsdom 依赖树整片 `TypeError` |
| 4 | profile 里放第二份 `@deepseek-ai/*` 会和宿主实例对不上 | 裸包名解析即可 | cordis 服务/符号全错，插件互相看不见 |
| 5 | 启动配置由 DSHM 每次启动重写 | 把酒馆写进 profile patch | 重启后酒馆自动加载、无法「默认关闭」 |
| 6 | ArkWeb 的 `localStorage` 不能作为唯一开关 | 前端开关 + 刷新 | 只能关 UI，关不掉 host 的回合与后台任务 |
| 7 | Profile 目录下 `settings` 写入会被 DSHM 覆盖 | 桌面无此问题 | 配置要落在 `profile-data` / home patch |

## 改写一：模板引擎从 fork 改成 worker_threads

模板引擎（`lib/domain/server-template-runtime.js`）原来 `fork()` 一个子进程跑
`server-template-worker.js`，用 `process.send` 传历史与结果。端侧没有子进程，
改成：

- `startInProcess()`：`new Worker(new URL('./server-template-worker-thread.mjs', import.meta.url))`
- `MessageChannel` 传历史 RPC（host 侧 7s 超时，避免历史读被阻塞）
- worker 内把 `process.send` / `process.on('message')` 映射到 `parentPort`，
  并在 `import()` 完成前**缓存消息**（端侧 import 慢，`initialize` 曾经直接丢掉）
- `WebAssembly` 给一个 `instantiate` 永远不 resolve 的桩：让 try/catch 里的
  WASM 探测走「不可用」分支，而不是 `ReferenceError` 打死 worker
- `resourceLimits`：maxOldGenerationSizeMb 1536（模板）/ 1024（脚本）
- 步骤日志写 `$DSH_HOME/tavern-worker.log`，卡住时能看出停在哪一步

脚本执行器（`server-script-executor.js`）同理：`vm` + worker thread，
`--experimental-vm-modules` 在 worker 里开。

## 改写二：加载/解析的三层钩子

端侧不允许「复制一份核心」。所有 `@deepseek-ai/*` 必须解析到宿主正在用的那份：

1. `registerHooks({ resolve })`：parent 在 `/node_modules/dsh-tavern-{host,remote}/` 或
   `dsh-better-sidebar/` 下的 `@deepseek-ai/*`，以核心目录的 `package.json` 为 parent 重解析。
2. `Module._resolveFilename` 兜底：DSH 的 ResolutionRouter 调 `resolve.paths` 抛
   `TypeError` 时，用 `Module._findPath` 自己找一次（只对 `dsh-tavern-host` 下的文件生效）。
3. worker 里再装一次（worker 是独立模块图，钩子不继承）。

核心目录不写死：从 `import.meta.url` 推出 `$DSH_HOME`，`$DSH_HOME/../cores` 下
挑 `@deepseek-ai/dsh-tools` 最新的那个版本目录。可用 `DSH_HOME` / `DSH_CORES` 覆盖。

## 改写三：加载时机 = 门

DSHM 每次启动按 bundle 模板重写 `profiles/ondevice/cordis.patch.yml`，所以
「把酒馆行写进去、加一个 `disabled` 字段」的开关方案在这里不成立 —— 下次启动
DSHM 会把它写回来，或者行本身就会被加载。

采用的方案（`dsh-tavern-gate`）：

- 启动行只有一个 ~200 行的 `gate`：路由 + 只读补丁，不 import host。
- 点开关 → `import('./tavern-host-entry.js')` → `ctx.plugin()`；
  关闭 → `fiber.dispose()`。状态只在内存里，重启一定是关的。
- 前端 bundle 的加载行（`dsh-tavern-plugin`）始终保持启用，但 `client.js`
  第一行同步问 `/api/tavern-gate/status`，门没开就立刻空实现返回（`XMLHttpRequest`
  同步请求，保证在模块工厂里就能决定是否继续）。

代价：前端 bundle（约 2MB）每次页面加载都会下载、解析一次，只是不执行。
换来的是「关闭 = 真的没有酒馆逻辑在跑」。

## 改写四：会话兼容补丁（只读）

酒馆写出的 `assistant/message` 会内嵌来源 stream，原生读取器会拒绝
（`assistant/message embeds its source stream and cannot carry sourceEventSeqs`）。
上游是在酒馆 host 里装补丁；端侧的问题是：**酒馆关掉之后**，这些会话还得能打开。

做法：`host-session-patch.js` 拆成 host 侧安装 + 前端源码分发。
gate 在开机时调用 `installHostSessionPatch()`（只包装 `SessionEventStream.readPage/follow`
的读取路径），把 `clientSource` 通过 `/api/tavern-gate/session-patch-client` 给前端，
前端 `eval` 后替换原型方法。酒馆打开时复用 `globalThis.__tavernGateSessionPatch`，
不重复包装。

这是唯一在「关」状态仍加载的酒馆代码。**取舍**：去掉它，关闭时的酒馆会话在原生界面
就是打不开的（`DSH_TAVERN_BOOT_PATCH=0` 即此行为）。

## 改写五：CPU 是抢的 —— 前台优先

端侧所有东西在一个 Node 进程里。模板引擎一渲染，正文流就卡；后台结算一跑，
候选行动就超时。实测最有效的三条：

1. **前台抢占**：非 transient 的模板调用开始时，如果正在跑的 transient 任务
   已经超过 2500ms，直接停掉它并递增 generation（旧结果作废）。
2. **排队取消**：排队中的后台任务按 `queueKind` 取消，别让它们在前台之后排长队。
3. **后台不抢显示同步**：正文回合 `running`、或候选/生图/结算 `busy` 时，
   推迟 `templateSync`（延迟 1.5s、最大退避 15s，回合结束后自然再次调度）。

配套的超时放宽（否则「慢」会被误判成「失败」）：

| 位置 | 上游 | 本移植 |
| --- | --- | --- |
| 模板渲染 | 180s | 180s（transient 90s） |
| host 侧模板 RPC 守卫 | — | 30s |
| `projectUserTemplate` | 无上限 | 45s 兜底，超时提示重试 |
| 世界书过滤 | 5min | 15min |
| 场景生图（规划/提交/轮询） | 5min | 15min |
| 候选行动 `submitTask`（前端） | 2s | 15s |

另外加了两个缓存/降级：历史读取的不可变快照缓存（TTL 60s、最多 128 份），
`legacy-template-display-repair` 与 `template-variable-display` 对端侧缺字段的容错。

## 改写六：cordis 服务可见性

`dsh-tavern-remote` 是启动行（`typert` 服务），`tavernSessionSignals` 由运行时加载的
host provide。cordis 的服务默认只对**子上下文**可见，兄弟行拿不到 → 前端一直显示
「生成中」。修正：host 把 `tavernSessionSignals` provide 到 `ctx.root`，
remote 侧用 `this.ctx.get('tavernSessionSignals')`（而不是属性访问）。

## 改写七：配置落在哪

DSHM 会重写 `profiles/ondevice/cordis.patch.yml`，所以：

- 用户级、必须持久的覆盖 → `$DSH_HOME/cordis.patch.yml`（home patch，DSHM 不改它）
- 酒馆自己的设置 → `profile-data/tavern/tavern-settings.json`（上游本来就放这）
- 权限默认值（`permission.defaultPreset: workspace-write`）→ home patch，
  由安装器补，避免每次重启被重置

**不要**手改 `profiles/ondevice/cordis.patch.yml`：改了也会在下一次启动被覆盖。

## 没做的

- 没有把酒馆合并成单个包（DSH 插件模型不允许：一个包一个 client 模块）。
- 没有在端侧重新构建前端 bundle（没有 node、没有 2GB 堆给打包器）；
  `client.js` 是上游构建产物 + 4 处小改，见 `patches/upstream/0001-*`。
- 没有实现上游的桌面更新器 / 端口管理 / 桌面启动器（DSHM 不需要）。
- 没有适配手机档（单屏）的完整交互：能显示，但侧栏与候选卡在小屏上比较挤。
